This is an Expo/React Native mobile application. Prioritize mobile-first patterns, performance, and cross-platform compatibility.

## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

Use `bunx` instead of `npx` if the project uses bun (`bun.lock` present).

```bash
npx expo install <package>  # ALWAYS use instead of npm/yarn/pnpm/bun add — resolves SDK-compatible versions
```

## Navigation & Routing

- Use **Expo Router** for all navigation. Routes live in `src/app/` — every file there is a screen, `_layout.tsx` files define navigators. Keep non-route code (components, hooks, utils) outside `src/app/`.
- Import `Link`, `router`, and `useLocalSearchParams` from `expo-router`.
- Docs: https://docs.expo.dev/router/introduction.md

## Building with EAS

Use EAS to build, sign, and submit the app in the cloud (`eas build`, `eas submit`) and to ship over-the-air updates (`eas update`) — no local Xcode or Android Studio required. Run EAS CLI as `bunx eas-cli <command>` in Bun projects, or `npx eas-cli@latest <command>` otherwise; substitute that for bare `eas` in docs examples.

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `npx expo run:ios|android` locally, or `eas build --profile development`.
- Prefer recommended Expo modules over third-party libraries, and check your available skills before adding dependencies. Docs: https://docs.expo.dev/versions/latest/index.md

- Password recovery takes the default Supabase e-mail link (web) or a numeric code (everywhere): `entrar.tsx` calls `resetPasswordForEmail`; then the person opens the link, or types the code (`verifyOtp({ type: 'recovery' })`; a code template carries `{{ .Token }}`, see README). The link opens the Site URL with the session in the URL fragment, and the app handles it in this order. (1) Boot, before the router: `index.js` (package.json `main`, a custom Expo Router entry) imports `src/lib/recoveryLinkBoot.ts` before `expo-router/entry`, because expo-router captures the address when it loads and writes it back later; the boot module parses the address (`parseRecoveryLink` in `src/lib/recoveryLink.ts`: a `type=recovery` fragment, or an error callback, i.e. `error`/`error_code`/`error_description` in the fragment, or `error` together with one of the other two in the query), strips it with `history.replaceState` and keeps the result in a module variable (no global; no-op on native; if stripping fails no session comes from the link). A link pasted into a tab where the app is already open only changes the fragment, so the boot module also listens to `hashchange` and reloads the page when the new address is such a link. Keep that import order (`@expo/metro-runtime`, the boot module, `expo-router/entry` last), and keep the boot module importing nothing but `recoveryLink.ts`, which imports nothing. (2) `createRecoveryLinkHandler` (pure, everything injected by `src/lib/auth.tsx`) checks the token before `setSession`: a plain `GET /auth/v1/user` with the anon key (10 s timeout, 3 attempts on connection problems, never a Supabase client) says whose token it is, so a rejected token leaves the stored session untouched; if another account is signed in it asks first (naming both e-mails) and signs that account out through `signOut` (`src/lib/session.ts`). (3) Marker before session: `beginRecovery` stores the marker and only resolves once it is written (if the write fails it rejects and no session comes from the link); it returns an undo, used if `setSession` fails, that restores the previous marker only while the marker still belongs to that attempt (a second key, `kotii:password-recovery-by`, says which attempt wrote it, because two tabs can write the same user id; every write, ownership check and undo of the marker runs one at a time, across tabs too, through a Web Lock, like the reminders); only then the tokens go to `supabase.auth.setSession`. After `setSession`, `ensureRecovery` checks again that the stored marker is the one of the session's user (another tab may have replaced it meanwhile, and the server decides whose session it is) and rewrites it if not; if the marker cannot be read or written (here or in `beginRecovery`), no session stays: the app signs it out. While the handler is pending AuthProvider releases no session to the router, but a SIGNED_OUT still runs its cleanup. `detectSessionInUrl` stays off; never hand URL tokens to the Supabase client before that check. A failed link is kept in `src/lib/linkNotice.ts`: `entrar.tsx` shows it with the recovery step open, `_layout.tsx` as a notice when an account is signed in. The notice lives while Entrar is open (cleared on unmount), and while the link is being checked `_layout.tsx` shows "Abrindo o link do e-mail…" instead of a blank page (`openedByRecoveryLink`). `src/lib/__tests__/authProvider.test.tsx` pins the order in AuthProvider. The copy for error callbacks is neutral on purpose: Supabase's error redirect is the same for every e-mail link and does not say which kind failed (sign-up confirmation or recovery). The marker is per user, in AsyncStorage (`src/lib/passwordRecovery.ts`; set by `beginRecovery` for the link and by `PASSWORD_RECOVERY`/`startRecovery` for the code), and `_layout.tsx` shows only `nova-senha` for that user until `USER_UPDATED` (also after a reload, on reopen, and in other tabs, which follow the marker through the window `storage` event, including a tab already signed in as that user); the marker goes away on save, "Cancelar e sair" or a password sign-in, never on a background SIGNED_OUT. Links always open the website (native has only the `kotii://` scheme), so native recovery ends there or uses the code. Auth errors are translated in `src/lib/authErrors.ts` (by `AuthApiError.code`, then text). Jest cannot see the router rewriting the address: after touching this flow, also check the exported web build in a browser.

- House reminders ("Avisos da casa"): `planHouseReminders` in `src/domain/houseReminders.ts` is the pure plan; each device chooses its kinds (`HOUSE_REMINDER_KINDS`: bills, documents, chores, appointments, events, vaccines, weather, eve). The `eve` kind ("Resumo de amanhã") is one notification at 20:00 on each of the next 7 evenings whose next day has something (`eveSummary`: consultas, family commitments and birthdays (`calendarEntries` of that day, so a "não vai ter" day is out and who takes / picks up is that day's), bills, vaccines, chores and manutenções, documents, warranties; only dates the data already has, never the Agenda's "previsão" repetitions; autopay bills and routine stay out, routine being a chore that is `daily` with an interval up to `EVE_ROUTINE_DAYS` (3) or a weekly commitment occurrence with the usual people (`entry.routine`), which would make it ring every night or every other night with nothing new; a new source of items is one entry in `EVE_ORDER`, its field in `EveSummaryInput` and one list in `eveItems`). Order: what has a time first, consultas and commitments together by the hour (same hour, the consulta first), then commitments without a time, birthdays and the rest source by source. The summary lists the commitments whatever the `events` kind says: the kinds only decide each thing's own reminders. Item texts: a commitment is "16h Festa do João (Ana, Carla leva)" (short time, title and `entryShortDetail`: whose it is and the ride, with the name only once when the commitment belongs to who takes, or to who only picks up: "Beto leva e busca") and a birthday "Aniversário de Ana (faz 8 anos)"; a bill without a value is "Conta: X" (unless its name already starts with "Conta"); a vaccine is "Vacina de Bia: …" ("de", because "da"/"do" would guess a gender), and two or more of the same person are one item ("Vacinas de Bia: A e B"); a consulta with no "2 horas antes" reminder (before 9h, `appointmentLeadTime`) carries its place, and a commitment whose day reminder does not exist (before 1h) or would ring before 07:00 (`EVENT_EARLY_TIME`) carries its place and "Levar: …" ("6h30 Passeio (Ana, Carla leva), Portão 2. Levar: lanche": what the 19:00 reminder that the summary replaces would have told; a later commitment, or one without a time, leaves both to its own day reminder). Those tails only get the room the items leave: first every place, in the order of the items, then each "Levar: …" (only after that item's whole place), each one whole, cut with "…" or left out when less than its minimum is left (`EVE_PLACE_MIN`, `EVE_BRING_MIN`); a commitment's "Levar" never takes the place of a later consulta. The text: at most 4 items written (with more, 3 and "e mais N") and 180 characters. When they run short, the plain cut (`fitTexts` over the whole texts: the longest are cut with "…" at the end, the short ones stay whole) is the starting point, and it is what every item that is not a commitment gets, always: a bill, a vaccine or a consulta never shrinks for a commitment's sake. The plain cut also stays for the commitments when it leaves every parenthesis readable (whole, or missing only the end of its last verb, with at least `EVE_VERB_MIN` letters of it: "Vó Maria bus…"). Otherwise (`fitItems`) each commitment's parenthesis is kept apart (`EveItem.detail`) and whole, and the commitments' titles (a commitment without a parenthesis is all title) share what the parentheses and the other items' plain cut leave. A commitment whose cut title would keep fewer than `EVE_TITLE_MIN` (12) letters, not counting the hour, goes back to its plain cut, with the room that cut gave it, and the others share the rest. A cut inside a parenthesis of the title itself moves back to before it when 12 letters remain, and no cut leaves a loose comma or a just-opened parenthesis (" (", " (A", " (An") before the "…". A day with only bills still gets its summary (the bill's own 9h reminder is another moment). While the kind is on, a consulta or a commitment written in a summary (not one left in the "e mais N", and only where that evening has a summary) gets no 19:00 eve reminder of its own (the hint in the settings list says so; `carried` is keyed by source and id, a commitment occurrence being id@date as in its reminder keys), and that summary takes the place of that 19:00 reminder in the limit queue: `standIn` for a consulta's (ahead of every other 19:00 of that evening), `forEvents` for commitments' only (exactly where the first eve it replaces would sort). A summary that stands in only for commitments counts in the commitments' part of the limit, like the eve it replaces; past that part it is a plain summary (with the kind off that eve would not fit either). If plain summaries of earlier evenings would still push a stand-in out, the farthest kept plain summary leaves and the cut is redone. So turning the kind on never costs a consulta or a commitment an eve warning that a summary replaces (a test over random houses pins it), except between 19:00 and 20:00, when tonight's summary is an extra reminder in the place of an eve that has already passed; an own 19:00 that no summary carries (an evening beyond the 7 nights, or an item left in the "e mais N") is subject to the accepted cost below. The limit: the family commitments are first cut to their share (see the Family calendar note), and the rest is one sort: own reminders by the time they ring, and the plain summary of evening D right after every own reminder dated up to D+1 (the day it talks about) and before those dated D+2 or later; then the plan is cut. So a plain summary never displaces a reminder of the day it talks about or of earlier days (a commitment of those days can still be out because of its share), and the farthest evenings go first. Accepted cost: with the summary on, an own reminder two or more days away may wait for the window to move (the plan is redone every time the app opens); in a house whose routine of commitments fills the free places, that happens at the default limit too. With the kind off the plan is exactly what it was before the kind existed. `syncHouseReminders` holds the kind as unknown (what is scheduled stays, nothing is replanned) while consultas, vacinas, the family calendar (`family`) or the equipment list have not loaded (on a database without the commitments tables the calendar still arrives, with the people only, so the summary does not wait); `eve` enters the unknown set only when the kind is on, so nothing changes for a device that does not use it. Two accepted corners of that held state, both gone at the next complete sync: the consulta's own 19:00 (and the commitment's, when what is missing is not the family calendar) is planned again next to the held summary (two notifications that night rather than none), and the held summaries keep their slots, so under a short limit the farthest own reminder can be left out (charging the held summaries last is not safe: it could cancel the only eve warning of a consulta). In the notification data the summary carries `reminder: <key>:<householdId>`, because on web that value is the notification tag and the summary key has no record id (two houses on the same evening would replace each other); the plan key has no house in it (the stored signature is the plan plus `|casa:<householdId>`, as for every kind: that suffix is what re-schedules, once, the reminders saved before their data carried the house, so it must stay), and the weather tip (`weather:dia:…`) still shares its tag between houses.

- "Estou indo ao mercado" (`src/domain/marketTrips.ts`, `src/data/marketTrips.ts`, `src/features/MarketTrip.tsx`): `announce_market_trip` creates a `market_trips` row (the household reads it, writes only through the functions; the list is checked again `FOR SHARE` after the per-person advisory lock and the household `FOR SHARE`, always in that order, so a list archived meanwhile answers `P0002`; the same person and list within 30 min returns the live trip, after that the new trip ends that person's earlier live trips of the list with their queued notices (after the notification loop, so subscriptions are locked before schedule rows), 5 new trips per person per house in 24 h, then `NK005`) and queues one `'once'` row with `fire_at = now()` in the `push_schedule` of each browser of the other current members, so the unchanged `send-push` delivers it; a browser whose schedule is full (`NK003`) or whose subscription vanished mid-loop (FK violation) is skipped without failing the others. The 24-hour cap (a rolling window, not the calendar day: the refusal says "nas últimas 24 horas") is counted in `market_trip_log` (one row per new trip, no FK to the list, rows older than 24 h purged on each call through the `created_at` index; RLS on, no policy, nothing granted to `anon`/`authenticated`), because the trips cascade away with their list. Title and body are built on the server from the stored names (`push_text`), never from the caller, and `data` is `{ reminder: 'ida:<trip id>', server: true, householdId }`; `push_text` writes its character classes with `\uXXXX` escapes only (no raw invisible or bidi character in the file, in `scripts/db/test.sql` either), keeps U+200C/U+200D (emoji sequences), the variation selectors (U+FE00–FE0F, U+180B–180D, U+180F, U+E0100–E01EF; U+180E, the Mongolian vowel separator, becomes a space) and the combining marks (U+0300–036F, U+1AB0–1AFF, U+1DC0–1DFF, U+20D0–20FF, U+FE20–FE2F), which belong inside real names, but counts none of them (nor the tag characters) as visible, and returns empty for a name with nothing visible (then the title says "Alguém da casa" and the body drops the quoted list name). The Hoje banner cleans the list name the same way (`tripListName` in `src/domain/marketTrips.ts`, with copies of the two classes as `PUSH_TEXT_HIDDEN` and `PUSH_TEXT_INVISIBLE`, plus U+0000): a Jest test parses the newest `push_text` in the migrations and fails if they diverge, so a change to `push_text` changes them too. An `AFTER DELETE` trigger on `household_members` (`member_left_market_trips`) covers `leave_household` and `remove_member` without re-creating them: it ends that person's live trips in that house (with their undelivered notices) and deletes that house's undelivered server rows from that person's browsers. Archiving a list ends its live trips with their undelivered notices (`shopping_lists_end_market_trips`, after an update of `archived_at` from null to a date only: a rename or an unarchive changes nothing; archiving is a plain client update, also from installed apps), and a trip that leaves the table takes its undelivered notices with it (`market_trips_gone`, after delete: the list's cascade, the 7-day purge, a deleted household). The leave and the archive triggers end every trip first, in one statement that collects the ids, and only then delete those trips' notices, in another (`using unnest(ids)`): one trip and its notices at a time, an archive could hold the notice of one member's trip to someone leaving the house while it waited for the trip of the one leaving, whose leave, holding that trip, waited for that notice (40P01); `scripts/db/test.sql` pins the order with a test-only trigger on `push_schedule` (the re-announce cleanup in `announce_market_trip` keeps one statement: it ends one trip at most, the person's earlier one on that list). The archive trigger takes no household lock: with the list already locked, waiting for the household could cross a last-member leave, which locks the household and, to delete it, waits for the list. - Receipt line without a value ("sem valor"): no database change and no change to the readers. A line is without value when its `total_price` is 0 in cents, whatever its unit price (`hasNoValue` in `src/domain/receiptItem.ts`); a free item looks the same in the data, so the app asks and never decides. `src/domain/receiptGap.ts` holds the rules and every sentence the receipt screen (`src/app/nota/[id].tsx`) shows about it: the difference between `receipts.total` and the sum of the lines in integer cents (`TOTAL_TOLERANCE_CENTS`, 5), the header notice, the question on the line, the suggestion (only with a receipt total, exactly one line without value and the total above the sum by more than the tolerance: "Usar R$ …" saves that total and the unit price that follows from the quantity, `unitPriceFromTotal`), the question before confirming (it only says the line enters spending as R$ 0,00; asked with `askYesNo` under the tap lock, so a double tap asks once) and the receipt total a draft lets the person fix (`readReceiptTotal`, empty or 0 = null). A total not above zero is no total (`hasReceiptTotal`: the photo reader can store 0, and spending already reads it that way): no notice, no suggestion, and the row says "informar". The total is saved only on drafts, by its own mutation (`useSetReceiptTotal`, `.eq('status', 'draft')`: on a receipt confirmed on another phone nothing is written and the refetch shows the confirmed receipt), and "Confirmar nota" with the total field open saves the typed total first (unreadable: a notice and nothing else). Nothing is filled in silently: a value is written only after a tap, and "Deixar sem valor" is state of that review, not stored. The editor opens such a line with both price fields empty (`receiptItemForm`), so a unit price typed alone computes the total; saving with both still blank is refused, with a message that says 0 leaves the line without value. A zero typed on purpose is the answer "Deixar sem valor" for that line, on a new line too (`useSaveReceiptItem` returns the id the database gave it, so the line does not ask when the refetch brings it). The lines of a confirmed receipt stay read-only with one exception: a line without value can get its value, and only that: the unit price and the total (`useFillReceiptItemValue` writes those two columns, on drafts too; the quantity and the unit of a confirmed line were already copied to the pantry by `confirm_receipt`, so they are shown and not edited; who paid is still editable). A write that matches no row is not an error for the database, so the two guarded writes ask for the row back: a total saved on a receipt that is no longer a draft stops "Confirmar nota" (the screen becomes the confirmed receipt), and a value written whose receipt does not come back (the refetch fails, or takes more than 4 s) leaves the line without its question for as long as the screen shows the read from before the write (`savedAt`, on a confirmed receipt too: another "Usar" or "Preencher" would find the line already with a value and say it was not saved) and, when the refetch failed, tells the person the value was saved (never after a write that matched no row: that one already said the value was not saved). "Confirmar nota" never goes with a read of the receipt older than what the screen wrote: every item write of the screen (a value, a line saved or added in the editor, a removed line) goes through `settleValue`, and when its refetch does not come back, or the write itself got no answer, the screen remembers which read was left behind (`staleRead`, taken from `useReceiptReadAt` and compared with the query's `dataUpdatedAt`); the next tap on "Confirmar nota" then refetches the receipt and asks for the tap again (`catchUp`), instead of confirming without the new line, which would stay without product, pantry and list and could not be fixed on a confirmed receipt. That write is `useFillReceiptItemValue`, which "Usar R$ …" also uses on a draft: no description, filtered on `total_price = 0`, with `.select('id')` so a write that matched nothing (the line already has a value, or is gone) tells the person instead of dropping the value in silence, invalidating what deleting a receipt invalidates plus the receipt itself; from that tap (or a line saved or removed in the editor) until the receipt has been refetched, "Confirmar nota" is busy (`settleValue` in the screen). A zero is not a price in what the app reads (`src/data/market.ts`): `usePriceHistory` and `usePriceObservations` ask only for `unit_price > 0`, so a store's earlier real price takes the place of the zero, and `fetchLatestPrices` drops the zero rows from what it returns (same query and paging); the `latest_prices` view keeps one row per product, store and unit, so on a database without the migration `20261014130000_price_views_no_zero.sql` a store whose latest row is a zero shows no price for that product until the next real purchase. That migration puts `ri.unit_price > 0` in the `price_observations` view (`latest_prices` reads from it), and from then on such a store shows its latest real price; the filters in the app stay, for the database that does not have it yet. A line with total 0 and a unit price above 0 still counts at that unit price.

- Shared prices ("Visto em outras casas", `supabase/migrations/20261014120000_shared_prices.sql`): the only data readable across households, so these are rules for any future work, not details; when in doubt, share less. One table, `shared_prices` (store CNPJ, `store_uf`, `store_name`, item key, unit, purchase day, price, and `visible_on`, the day the row becomes readable): no household, user, receipt, row id, sequence or timestamp, and no column default; one row per (store CNPJ, item key, unit, day), so a second household buying the same thing in the same store on the same day lands on the same row and the writers can never be told apart or counted (`scripts/db/test.sql` pins the exact column list; a new column has to pass "can it point back?" first). The phone field holds one number: `parsePhone` splits the text on anything that is not a digit, space, parenthesis, dot, `+` or hyphen and gives null when more than one piece has digits, so an extension or a second number never joins into somebody else's number (`phoneHint` then says to keep one number there). Inside one piece the same goes for a complete local number in its usual shape (digit groups 4 + 4 or 5 + 4) followed by another group (`localNumberThenMore`: "3456-7890 (22)", "98765-4321 (11)", "011 3456-7890 22", "+5511 3456-7890 22", "5511-3456 1234"), with the same hint. The local number is read where the person wrote it: a last group alone in parentheses ("(1234)", "(22)") is never its second half (it is the extension or the DDD written at the end: "5511 3456 (1234)" gives null); among the pairs, the last one whose halves are joined by a hyphen with no space around it ("3456-7890") wins when the pair forms a local number (`localNumber`: none starts with 0 or 1, and a 5 + 4 pair is a mobile, with the 9) and does not start right after a "+" (there the hyphen follows the country code and the DDD: "+5511-3456 7890" is valid); a spaced " - " separates ("5511-3456 - 1234" gives null). With no such pair, the last pair, because it ends what was typed: the groups before it (the 55, the zero and the carrier, the DDD) never count, even one of four digits like half a number, so "+5511 3456 7890", "5511 3456 7890" and "5511.3456.7890" (the 55 glued to the DDD) are valid ("+5511 3456-7890" and "5511 3456-7890" are valid too, through the hyphen rule). A hyphen right after the 55 glued to the DDD, without "+", reads as the hyphen inside the local number, so "5511-3456 7890" gives null with the one-number hint, like "5511-3456 1234". Not for a foreign "+" number, whose groups are other, nor for a toll-free number written without "+" (the piece's digits match `TOLL_FREE`, as in "0800 7010 102", whose groups are not 4 + 4). A piece that reads as no number but would without its last digit group gets the one-number hint too, not the "incomplete" one (`phoneHint`: "3456 7890 1234", "987654321 22"). Known limits (pinned in `src/domain/__tests__/providers.test.ts`): a local number typed with no separator and followed by an extension can read as one number ("34567890 (22)" is (34) 5678-9022), and after a number without DDD whose first digits are 55 and a DDD, a four-digit extension without parentheses reads as part of the number when the number has no hyphen joining its halves ("5511 3456 1234") or the extension is joined by another hyphen ("5511-3456-1234"): both have the groups of the 55 glued to the DDD and read as +55 11 3456-1234. Digits starting with "00" give null (the international prefix: in Brazil a carrier code follows it, in Europe the country code, so the zero-plus-carrier reading would make a Brazilian number of it), with a hint to write it with "+".
