## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

## Navigation & Routing

- Use **Expo Router** for all navigation. Routes live in `src/app/` — every file there is a screen, `_layout.tsx` files define navigators. Keep non-route code (components, hooks, utils) outside `src/app/`.
- Import `Link`, `router`, and `useLocalSearchParams` from `expo-router`.
- Docs: https://docs.expo.dev/router/introduction.md

Run EAS CLI as `bunx eas-cli <command>` in Bun projects, or `npx eas-cli@latest <command>` otherwise; substitute that for bare `eas` in docs examples.

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `npx expo run:ios|android` locally, or `eas build --profile development`.
- Prefer recommended Expo modules over third-party libraries, and check your available skills before adding dependencies. Docs: https://docs.expo.dev/versions/latest/index.md

Run `npm run test:db` (temporary Postgres + Supabase stubs in `scripts/db/`) after schema changes; it applies the migrations dated from `NO_DEFAULT_GRANTS_FROM` (`scripts/db/test.sh`) on without the default table privileges, so a new table with a missing grant fails there, and the block of a new table in `scripts/db/test.sql` asserts each privilege on its own (`has_table_privilege` with a comma list is true when any one is held).

- Password recovery takes the default Supabase e-mail link (web) or a numeric code (everywhere): `entrar.tsx` calls `resetPasswordForEmail`; then the person opens the link, or types the code (`verifyOtp({ type: 'recovery' })`; a code template carries `{{ .Token }}`, see README). The link opens the Site URL with the session in the URL fragment, and the app handles it in this order. (1) Boot, before the router: `index.js` (package.json `main`, a custom Expo Router entry) imports `src/lib/recoveryLinkBoot.ts` before `expo-router/entry`, because expo-router captures the address when it loads and writes it back later; the boot module parses the address (`parseRecoveryLink` in `src/lib/recoveryLink.ts`: a `type=recovery` fragment, or an error callback, i.e. `error`/`error_code`/`error_description` in the fragment, or `error` together with one of the other two in the query), strips it with `history.replaceState` and keeps the result in a module variable (no global; no-op on native; if stripping fails no session comes from the link). A link pasted into a tab where the app is already open only changes the fragment, so the boot module also listens to `hashchange` and reloads the page when the new address is such a link. Keep that import order (`@expo/metro-runtime`, the boot module, `expo-router/entry` last), and keep the boot module importing nothing but `recoveryLink.ts`, which imports nothing. (2) `createRecoveryLinkHandler` (pure, everything injected by `src/lib/auth.tsx`) checks the token before `setSession`: a plain `GET /auth/v1/user` with the anon key (10 s timeout, 3 attempts on connection problems, never a Supabase client) says whose token it is, so a rejected token leaves the stored session untouched; if another account is signed in it asks first (naming both e-mails) and signs that account out through `signOut` (`src/lib/session.ts`). (3) Marker before session: `beginRecovery` stores the marker and only resolves once it is written (if the write fails it rejects and no session comes from the link); it returns an undo, used if `setSession` fails, that restores the previous marker only while the marker still belongs to that attempt (a second key, `kotii:password-recovery-by`, says which attempt wrote it, because two tabs can write the same user id; every write, ownership check and undo of the marker runs one at a time, across tabs too, through a Web Lock, like the reminders); only then the tokens go to `supabase.auth.setSession`. After `setSession`, `ensureRecovery` checks again that the stored marker is the one of the session's user (another tab may have replaced it meanwhile, and the server decides whose session it is) and rewrites it if not; if the marker cannot be read or written (here or in `beginRecovery`), no session stays: the app signs it out. While the handler is pending AuthProvider releases no session to the router, but a SIGNED_OUT still runs its cleanup. `detectSessionInUrl` stays off; never hand URL tokens to the Supabase client before that check. A failed link is kept in `src/lib/linkNotice.ts`: `entrar.tsx` shows it with the recovery step open, `_layout.tsx` as a notice when an account is signed in. The notice lives while Entrar is open (cleared on unmount), and while the link is being checked `_layout.tsx` shows "Abrindo o link do e-mail…" instead of a blank page (`openedByRecoveryLink`). `src/lib/__tests__/authProvider.test.tsx` pins the order in AuthProvider. The copy for error callbacks is neutral on purpose: Supabase's error redirect is the same for every e-mail link and does not say which kind failed (sign-up confirmation or recovery). The marker is per user, in AsyncStorage (`src/lib/passwordRecovery.ts`; set by `beginRecovery` for the link and by `PASSWORD_RECOVERY`/`startRecovery` for the code), and `_layout.tsx` shows only `nova-senha` for that user until `USER_UPDATED` (also after a reload, on reopen, and in other tabs, which follow the marker through the window `storage` event, including a tab already signed in as that user); the marker goes away on save, "Cancelar e sair" or a password sign-in, never on a background SIGNED_OUT. Links always open the website (native has only the `kotii://` scheme), so native recovery ends there or uses the code. Auth errors are translated in `src/lib/authErrors.ts` (by `AuthApiError.code`, then text). Jest cannot see the router rewriting the address: after touching this flow, also check the exported web build in a browser.
- House reminders ("Avisos da casa"): `planHouseReminders` in `src/domain/houseReminders.ts` is the pure plan; each device chooses its kinds (`HOUSE_REMINDER_KINDS`: bills, documents, chores, appointments, vaccines, weather, eve). The `eve` kind ("Resumo de amanhã") is one notification at 20:00 on each of the next 7 evenings whose next day has something (`eveSummary`: consultas, bills, vaccines, chores and manutenções, documents, warranties; only dates the data already has, never the Agenda's "previsão" repetitions; autopay bills and routine chores stay out, routine being `daily` with an interval up to `EVE_ROUTINE_DAYS` (3), which would make it ring every night or every other night with nothing new; a new source of items is one entry in `EVE_ORDER`, its field in `EveSummaryInput` and one list in `eveItems`, which is how compromissos and aniversários will come in). Item texts: a bill without a value is "Conta: X" (unless its name already starts with "Conta"); a vaccine is "Vacina de Bia: …" ("de", because "da"/"do" would guess a gender), and two or more of the same person are one item ("Vacinas de Bia: A e B"); a consulta with no "2 horas antes" reminder (before 9h, `appointmentLeadTime`) carries its place, which only gets the room the items leave. A day with only bills still gets its summary (the bill's own 9h reminder is another moment). While the kind is on, a consulta written in a summary gets no "Consulta amanhã" of its own (the hint in the settings list says so), and that summary takes the place of that 19:00 reminder in the limit queue; if plain summaries of earlier evenings would still push it out, the farthest kept plain summary leaves and the cut is redone, so the consulta keeps an eve warning whenever its 19:00 would fit with the kind off. The limit is one sort: own reminders by the time they ring, and the plain summary of evening D right after every own reminder dated up to D+1 (the day it talks about) and before those dated D+2 or later; then the plan is cut. So a summary never displaces a reminder of the day it talks about or of earlier days, and the farthest evenings go first. Accepted cost: with the summary on, an own reminder two or more days away may wait for the window to move (the plan is redone every time the app opens). With the kind off the plan is exactly what it was before the kind existed. `syncHouseReminders` holds the kind as unknown (what is scheduled stays, nothing is replanned) while consultas, vacinas or the equipment list have not loaded; `eve` enters the unknown set only when the kind is on, so nothing changes for a device that does not use it. Two accepted corners of that held state, both gone at the next complete sync: the consulta's own 19:00 is planned again next to the held summary (two notifications that night rather than none), and the held summaries keep their slots, so under a short limit the farthest own reminder can be left out (charging the held summaries last is not safe: it could cancel the only eve warning of a consulta). In the notification data the summary carries `reminder: <key>:<householdId>`, because on web that value is the notification tag and the summary key has no record id (two houses on the same evening would replace each other); the plan key has no house in it (the stored signature is the plan plus `|casa:<householdId>`, as for every kind: that suffix is what re-schedules, once, the reminders saved before their data carried the house, so it must stay), and the weather tip (`weather:dia:…`) still shares its tag between houses.
- Notifications: `src/lib/reminders.ts` schedules everything. On native it uses local `expo-notifications`; on web the same calls go to `src/lib/webPush.ts`, which stores the schedule in `push_schedule`, and the `send-push` function (fired every minute by pg_cron) delivers it via Web Push to `public/sw.js`. Keep both paths behind the same reminders API.
- Shopping list ↔ receipt: list items are free text, so `confirm_receipt` removes the list items the user ticked in the review and learns `list_item_links` (list name key → product). Matching and keys live in `src/domain/listLinks.ts` (`listNameKey` must match the SQL check on `name_key`); the cart/receipt pantry de-duplication (`src/domain/cartPantry.ts`) uses the same links. The review also keeps product names standard (`src/domain/similarNames.ts`; what each tap does to the item is in `src/domain/receiptNames.ts`): a new product's name is checked against one index of the names the household already uses (products, open list items, recent purchases) plus the `COMMON_ITEMS` catalog. `igual` is the same words ignoring accent and plural, and ignoring order only when neither name has a role link ("Suco de laranja" is not "Laranja para suco"); sizes ("350ml", "1,5L" as one decimal size, "2 litros" = "2L"), a trailing letter ("Vitamina C") and "sem X" count as part of the name. `parecido` is one name containing the other. The product picker shows up to 5 similar names (among the loosely similar ones, household names come before catalog ones), including the names given to other items of the same receipt ("Nesta nota", a second small index). `suggestedName` is what the item card offers unprompted and must be high precision (in doubt, no chip): the best `confident` household name, never a catalog-only one. Confident means the household name fits at the start of the new name with the same size and what follows does not make another thing ("de"/"em" plus a non-packaging word, a word of the fixed `OTHER_THING` set such as "Leite coco", or a pair that some indexed name knows as one name, joined by "de"/"em" or by a hyphen: "Pão de queijo", "Couve-flor"; a hyphen nobody knows, as in "Banana-prata", is just a variety); a household product with a real size is exact (same sizes, so a pack is not the unit; after it only packaging words or a version word with its number, "Tipo 1") and only it may fit in the middle of a name. The catalog does not silence the household's generic name ("Leite" for "Leite Integral Italac 1L"); a longer indexed name, catalog or household, vetoes the chip only when it also fits the start loosely and is another thing ("Leite condensado" for "Leite cond moca"). A receipt abbreviation ("DETERG") counts when the fragment has a single reading, is at least half the word, does not end in a vowel and is not a real word; the vocabulary of real words is the catalog plus list items and purchases without a product, and a product's word only when it is not the start of a longer one. It only suggests: nothing is linked or renamed without a tap, and after "Usar" the card shows "Desfazer", which puts the item's override back exactly. The list tick is derived, not stored: `matchListItems` ticks a list item while the receipt line's product has its name; the review passes `sameListedName` for that, the same `igual` rule ("Limões" with the product "Limão", but not "Molho de tomate" with "Tomate para molho"), while `listRemovals` still sends the list item's own name and `listNameKey`. The list screen's market estimate (`src/domain/listEstimate.ts`: `estimateList` for the total and each item's cost, `pantryHits` for "Na despensa", `itemFacts`, `describeEstimate`, `estimateHeadline` and `describePantryHits` for the texts) and "Onde comprar" (`recommendation.ts`) are one calculation: the price of each list item in each store comes from one rule, `listStorePrices` in `listEstimate.ts`. The item's product is its own or, when it has none or that product has no price, the most recently bought among the products linked to the name via `LinkIndex.productsFor` and the same-name product (when two products have the same name but for the accent, the one with the most recent price, then the lowest id, never array order); in a store, the price is that product's in its usual unit, then that product's in another unit, then, only when the product came from the name (the item has no product, or its product has no price anywhere), another product's linked to the name (always shown as approximate, "~"), and for a store without any of them the product's average times the store's price level (`storePriceIndex` in `src/domain/priceLevel.ts` over all the household's prices: positive prices only, one price per store in each product (the newest when the rows carry `purchasedAt`, else the store's average), shrunk towards 1 when few products are shared, clamped). Units follow `src/domain/units.ts`: g↔kg and ml↔l convert exactly; any other pair counts one kg, one litre or one unit whatever the quantity (never one gram) and is flagged approximate, "~". Prices enter the rule through `comparablePrices`: per g becomes per kg and per ml per litre (rounded to the column's 4 decimals), and each store keeps one row per product and unit, the newest, so the last price, "preço bom", the average and every sentence compare and show kg and litre (`ItemEstimate.unitPrice` keeps 4 decimals; only `cost` is in cents). `estimateList` uses that answer for the chosen store and `onde-comprar.tsx` passes the same answer to `recommendStores` as `priceAt` (store totals, each row's cost and its note, `storePriceNote`), so both screens give the same total for the same items and store, always ("Onde comprar" counts what is still to buy, the list's "Falta comprar"); a Jest test pins it (named cases and a seeded sweep of random lists, every store). Without `priceAt`, `recommendStores` prices from the item's `productId` in one unit for every store, which is not the list's calculation: screens always pass it. The estimate uses the last price paid or, with a chosen store (kept in memory per list for 6 hours via `currentStoreChoice`, never in AsyncStorage, and ignored until the stores query has its name), that store's answer; "preço bom" is the lowest price of that same product. Items without any price never count, and the headline says "A lista deve dar" only when every item is priced (otherwise "Os N itens com preço devem dar"). "Na despensa" states what the app knows (unexpired pantry rows of the same product, of a product the person linked to the name, or with the same name; no quantity when the rows are different products) and is suppressed for what `ranOutItems` (`src/domain/restock.ts`: everything past its usual interval, with no list exclusion and no 3× give-up, for as long as three trips still fit in the 180-day history; the "Acho que acabou" strip is `restockFrom` over the same result, read from the history once per screen) thinks ran out, except pantry rows bought after the last purchase that guess knows (`lastAt`; more than `SAME_TRIP_DAYS` after it, and only while the row itself is younger than the usual interval), which are fresh stock. A guess without a product (free-text "Leite" ticked on the list) also counts for the product the receipts linked to that name when it is the only one, and so for a list item backed by that product; a guess that has a product never passes to another one. The list screen reads `ranOutItems` without `listKind` (the guess does not depend on the kind of list; only the strip is filtered, with `fitsList`) and computes `pantryHits` only when the purchase history is loaded, so a device that never loaded it shows no badge; the screen is never gated on that query, nor on links or products: when those two did not arrive (failed, or offline and never seen; not while the first fetch is on its way) the card adds `uncheckedPricesNote`. `latestPrices`, `stores` and `listLinks` are in the persisted query cache so it works offline; `fetchLatestPrices` (`src/data/market.ts`) reads `latest_prices` in pages of 1000 ordered by the view's key and throws rather than return a truncated list. "Mandar a lista" (`src/features/ListShareSheet.tsx`) hands the list to someone without the app as plain text built in `src/domain/listShare.ts` (what is still to buy, in the screen's `compareForShopping` order; no prices, pantry, photos or names of people or of the house): a `wa.me` link, the system share sheet or the clipboard, and nothing is stored or sent by the app itself.
- Bill above its usual ("Conta acima do normal"): no table of its own, everything is computed from `bill_payments` in `src/domain/billUsual.ts` (rule and texts). The usual of a monthly bill is the average of up to 6 payments, by `due_on`, from the 6 months before the due date being judged (never that due date's own payment; R$ 0,00 payments do not count; at least 3, else there is none; yearly and one-off bills never have one); a value is above when it is at least 20% AND at least R$ 10,00 over it; there is no "below" notice; a fixed amount the person raised only counts until one payment of exactly that value exists in the window. Shown in `PayBillModal` (hint under "Valor pago", following what is typed), the bill screen (`conta/[id].tsx`: notice for the stored boleto or fixed amount, badge on each history payment judged against the payments before it), and as a badge in `BillsPanel` and the Hoje tab; the Nuke snapshot carries it as ready text. The lists read all bills' recent payments in one query (`useRecentBillPayments`, 12 months by due date, so a bill some months overdue keeps its badge; its key starts with `billPayments`, so paying, undoing or deleting a bill refetches it) and show no badge while it loads or fails; every place that judges payments (lists, bill screen note, pay hint, Nuke) reads them through `settledData` (`src/lib/settledData.ts`), so rows kept from before a refetch, or after a failed one, never decide a notice. Not in reminders, the Resumo/budget math or the finance advisor.
- "Mercado do mês" (`src/app/mercado.tsx`, opened from Finanças → Resumo with `?mes=AAAA-MM` and from Finanças → Notas): where the market money of a month went. The top is always the month, "R$ X em N idas" and the comparison; under it a `Segmented` shows one part at a time (Itens, the default: first 10 then "Ver todos"; Categorias: every bar, and tapping one goes to Itens with all the items of that category and a chip to clear it; Idas; Mercados), kept in the URL as `?aba=` like the month (`viewFromParam`, unknown value → itens; `router.setParams`, which merges with `mes` and does not push history). One collapsible line, "Como este total fecha", shown only when the month has something to say (`closing`), holds the difference rows, the lines without value, the pharmacy line and the month's drafts (the three newest, each opening its own `/nota/[id]`, then "e mais N em Finanças > Notas" as text; nothing there navigates to the tabs); in a month without trips those rows are shown open under the empty state. Everything the screen shows comes from `marketMonth` in `src/domain/marketSpend.ts` (integer cents, and every text that depends on a number; the screen is thin), fed by `useMarketReceipts` (`src/data/marketSpend.ts`: the receipts of the month and of the previous one). What counts: the lines of confirmed receipts by purchase date (device timezone, the Resumo's month limits), limpeza, higiene, papel, bebê and pet included; the product categories the Resumo files as Saúde (`financeCategoryOfProduct(...) === 'saude'`) stay out and show as one line with what was paid for them, and a receipt whose lines are all pharmacy is not a trip (its whole total is pharmacy). Printed values, always: a line counts its `total_price` and is never scaled to the receipt total (that is `buildEntries`, for the Resumo). A receipt total different from the sum of its lines is shown apart, per month ("Descontos no total das notas"; "Nas notas, sem item lido", with the receipts listed), never netted between receipts. On a receipt with market and pharmacy lines that difference is split between the two sides in proportion to their printed sums (`receiptMoney`: `Math.round` for the market share, the remainder to the pharmacy, so both add to the difference and a trip can never be negative); with no printed value at all it stays whole on the market side as "sem item lido". The amounts are exact, but a receipt is listed "para conferir" only when its own difference is above `RECEIPT_CHECK_CENTS` (5 cents, the tolerance of `totalMismatch` in `src/app/nota/[id].tsx`; keep the two together), and the hint sentence only shows with a receipt listed. A receipt without total (null or 0) has no difference; a line without value counts zero and is counted ("N itens sem valor", whatever its category), and the copy never asks the person to fill it in: a confirmed receipt is read-only. The month total is what was paid (lines + the market share of the differences), and the shares are over the sum of the lines, so they add to 100% within rounding (each share is rounded on its own); when the two sums differ the screen says so (`shareBasis`, and "dos itens" in the spoken share). That total plus the pharmacy line equals what the Resumo counts from receipts in the month (Jest pins it, with a seeded sweep of receipts). `marketTotal` is the one function for the month total and the trip count: `marketMonth` takes its headline from it, and the entry row in the Resumo (`MarketMonthLink`) calls it on the receipts the Resumo already fetched (`useSpendingReceipts`: same query key and fetch as `useSpending`, which keeps returning the entries through `select`), so the two numbers cannot differ and the Resumo never runs this screen's query (the Resumo's own read is not paged: what it cuts, the row cuts too). A line's category is the product's, else the suggested one, else `outros`; an item is a product id, and lines without a product group by `listNameKey` inside their category, never by similarity (joining products is the person's decision). In the running month the total and the categories are compared with the previous month up to the same day (the rule of `previousMonth`), while each item shows the whole previous month's amount; with no market receipt in that window only the header says so and the categories say nothing. `fetchMarketReceipts` reads receipts and lines in pages by keyset (`order('id')`, `gt('id', last id)`, never offsets: a row deleted or inserted between two pages must not shift the next ones), only finishes when a page holds everything the server's exact count says is left (a short page is not proof of the end), and throws at its ceilings instead of truncating; it sorts receipts by purchase date and each receipt's lines by `position` afterwards. Lines are read by receipt ids, not embedded, because PostgREST's max-rows also caps embedded rows. The query key starts with `spending`: never persisted, invalidated wherever the Resumo is, and `useRenameProduct` invalidates `spending` too (a product's category and name change both screens). A paused first load (offline, nothing cached) shows a notice, not a spinner. It must not change `buildEntries`, the Resumo/budget numbers or the Nuke snapshot. `BarRow` (`src/features/finance/BarRow.tsx`) is the bar row both screens use (`labelLines`: 1 in the Resumo, 2 here).

- Finance advisor beta ("Consultor", shadow mode): bank data from Pluggy (MeuPluggy items whose Item IDs the owner pastes in `src/app/consultor/`) lives in private `fin_connections`/`fin_accounts`/`fin_transactions`, readable only by that user (`user_id = auth.uid()` + `current_household_id()` + `has_beta('finance')`, granted by a manual SQL insert into `beta_access`) and written only by the service role in the `finance` function (`map.ts` pure mapping, `sync.ts` orchestration with an injected Pluggy client and db, `index.ts` the service-role adapter; `_shared/pluggy.ts` is a plain-fetch client, no pluggy-sdk; sync on open if > 6 h or forced, 365 days until Pluggy has data then a window from a week before the last covered date (at least 60 days) with `deleted_at` tombstones; no webhooks; CPF hashes are HMAC with the `FIN_DOC_HASH_KEY` secret and CPFs are stripped from stored descriptions and names). It must not change the existing finance tables, the Resumo/budget math or the household Nuke snapshot; reconciliation with Kotii records (`src/domain/bankMatch.ts`) is read-only suggestions. Installment purchases count month by month: one `BankPurchase` per parcel the bank sent, dated purchase date + (n-1) months with its own amount, and `installment` carries the whole purchase (series key, purchase date and amount) for the comprometido (`futureInstallments`, once per purchase), refunds of the whole purchase and the Kotii receipt of the whole purchase (`reconcileWindow`, with records fetched from `kotiiRecordsStart`); parcels are read 24 months back (`financeInstallmentFetchStart`) so the first parcel dates the purchase (Pluggy only gives 12 months on the first sync; without the first parcel, the date comes from `purchase_on` or an estimate), plus, by id, any older parcel a "Só esta" rule or saúde mark points to (`ruleParcelIds`), and card credits (refunds) over the same 24 months. The one thing the app writes is the user's own category choices (`fin_category_rules`, own rows only, same RLS plus the beta FK; `src/app/consultor/lancamentos.tsx`): a rule per purchase (`p:<purchase key>`; on an installment purchase, a rule on any parcel's key covers all of them, read via `ruleKeys` and written to `ruleKey`) or for similar ones (`doc:<CPF hash>` or `m:<name without digits>`), applied in `groupPurchases` via `src/domain/bankRules.ts`; a chosen category never lets a person-like name reach the snapshot (`storeName` keeps using the automatic category) and choosing saúde makes the purchase sensitive for good: a trigger on `fin_category_rules` records the match_key in `fin_sensitive_keys` (read-only for the owner, same RLS and beta FK), plus the purchase's similar key on a "Só esta" choice (`similar_key`, so the mark survives a new transaction id), and changing or undoing the choice, or a "Só esta" over a saúde rule for similar ones, keeps it sensitive (`chosenSensitive` in `bankRules.ts`); a refund inherits its purchase's sensitivity (`linkRefunds`, or `refundOfSaudeStore` without a pair), and the consultor screen re-saves older per-purchase saúde choices with their similar key (`missingSimilarMarks`, `useRepairSimilarMarks`). Rules live in `src/domain/bank*.ts` and `financeAdvisor.ts`; the LLM never does arithmetic (numbers come precomputed in the snapshot), and the snapshot never carries CPF, account/agency numbers, boleto lines or people's names (names only from an allowlist: Pluggy merchant, non-MEI company, card purchase, and a person-like name only with a store category; sensitive categories only as totals). The chat (`nuke-finance`) is Anthropic-only (`FINANCE_MODEL`, default `claude-haiku-5-5`; fails closed without `ANTHROPIC_API_KEY`, never OpenRouter), uses the `finance` AI quota, and its history is memory-only (`src/features/finance/advisorConversation.ts`; never AsyncStorage/localStorage, and no `fin_*` queries in the persisted query cache).
