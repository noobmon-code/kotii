This is an Expo/React Native mobile application. Prioritize mobile-first patterns, performance, and cross-platform compatibility.

## Expo has changed — do not trust your training data

Expo ships breaking changes every SDK release. APIs you remember are likely renamed, moved, or removed. Before writing any code that touches an Expo, EAS, or React Native API:

1. Read the major version of the `expo` package in `package.json`.
2. Fetch the matching versioned docs: `https://docs.expo.dev/versions/v<major>.0.0/`
3. For anything else, fetch https://docs.expo.dev/llms.txt — an index of all Expo docs with corrections to common LLM misconceptions. Follow its links to the specific page you need; never answer from memory.

Use `bunx` instead of `npx` if the project uses bun (`bun.lock` present).

```bash
npx expo install <package>  # ALWAYS use instead of npm/yarn/pnpm/bun add — resolves SDK-compatible versions
```

Run lint and typecheck before declaring any task done.

## Navigation & Routing

- Use **Expo Router** for all navigation. Routes live in `src/app/` — every file there is a screen, `_layout.tsx` files define navigators. Keep non-route code (components, hooks, utils) outside `src/app/`.
- Import `Link`, `router`, and `useLocalSearchParams` from `expo-router`.
- Docs: https://docs.expo.dev/router/introduction.md

## Building with EAS

Use EAS to build, sign, and submit the app in the cloud (`eas build`, `eas submit`) and to ship over-the-air updates (`eas update`) — no local Xcode or Android Studio required. Run EAS CLI as `bunx eas-cli <command>` in Bun projects, or `npx eas-cli@latest <command>` otherwise; substitute that for bare `eas` in docs examples.
Docs: https://docs.expo.dev/eas/index.md

## Rules

- If `ios/` and `android/` directories do not exist, they are generated (Continuous Native Generation). Never create or edit them by hand — configure native behavior in `app.json` and config plugins.
- Expo Go only includes its bundled native modules. After adding a library with native code, the app needs a development build: `npx expo run:ios|android` locally, or `eas build --profile development`.
- Prefer recommended Expo modules over third-party libraries, and check your available skills before adding dependencies. Docs: https://docs.expo.dev/versions/latest/index.md

- Password recovery takes the default Supabase e-mail link (web) or a numeric code (everywhere): `entrar.tsx` calls `resetPasswordForEmail`; then the person opens the link, or types the code (`verifyOtp({ type: 'recovery' })`; a code template carries `{{ .Token }}`, see README). The link opens the Site URL with the session in the URL fragment, and the app handles it in this order. (1) Boot, before the router: `index.js` (package.json `main`, a custom Expo Router entry) imports `src/lib/recoveryLinkBoot.ts` before `expo-router/entry`, because expo-router captures the address when it loads and writes it back later; the boot module parses the address (`parseRecoveryLink` in `src/lib/recoveryLink.ts`: a `type=recovery` fragment, or an error callback, i.e. `error`/`error_code`/`error_description` in the fragment, or `error` together with one of the other two in the query), strips it with `history.replaceState` and keeps the result in a module variable (no global; no-op on native; if stripping fails no session comes from the link). A link pasted into a tab where the app is already open only changes the fragment, so the boot module also listens to `hashchange` and reloads the page when the new address is such a link. Keep that import order (`@expo/metro-runtime`, the boot module, `expo-router/entry` last), and keep the boot module importing nothing but `recoveryLink.ts`, which imports nothing. (2) `createRecoveryLinkHandler` (pure, everything injected by `src/lib/auth.tsx`) checks the token before `setSession`: a plain `GET /auth/v1/user` with the anon key (10 s timeout, 3 attempts on connection problems, never a Supabase client) says whose token it is, so a rejected token leaves the stored session untouched; if another account is signed in it asks first (naming both e-mails) and signs that account out through `signOut` (`src/lib/session.ts`). (3) Marker before session: `beginRecovery` stores the marker and only resolves once it is written (if the write fails it rejects and no session comes from the link); it returns an undo, used if `setSession` fails, that restores the previous marker only while the marker still belongs to that attempt (a second key, `kotii:password-recovery-by`, says which attempt wrote it, because two tabs can write the same user id; every write, ownership check and undo of the marker runs one at a time, across tabs too, through a Web Lock, like the reminders); only then the tokens go to `supabase.auth.setSession`. After `setSession`, `ensureRecovery` checks again that the stored marker is the one of the session's user (another tab may have replaced it meanwhile, and the server decides whose session it is) and rewrites it if not; if the marker cannot be read or written (here or in `beginRecovery`), no session stays: the app signs it out. While the handler is pending AuthProvider releases no session to the router, but a SIGNED_OUT still runs its cleanup. `detectSessionInUrl` stays off; never hand URL tokens to the Supabase client before that check. A failed link is kept in `src/lib/linkNotice.ts`: `entrar.tsx` shows it with the recovery step open, `_layout.tsx` as a notice when an account is signed in. The notice lives while Entrar is open (cleared on unmount), and while the link is being checked `_layout.tsx` shows "Abrindo o link do e-mail…" instead of a blank page (`openedByRecoveryLink`). `src/lib/__tests__/authProvider.test.tsx` pins the order in AuthProvider. The copy for error callbacks is neutral on purpose: Supabase's error redirect is the same for every e-mail link and does not say which kind failed (sign-up confirmation or recovery). The marker is per user, in AsyncStorage (`src/lib/passwordRecovery.ts`; set by `beginRecovery` for the link and by `PASSWORD_RECOVERY`/`startRecovery` for the code), and `_layout.tsx` shows only `nova-senha` for that user until `USER_UPDATED` (also after a reload, on reopen, and in other tabs, which follow the marker through the window `storage` event, including a tab already signed in as that user); the marker goes away on save, "Cancelar e sair" or a password sign-in, never on a background SIGNED_OUT. Links always open the website (native has only the `kotii://` scheme), so native recovery ends there or uses the code. Auth errors are translated in `src/lib/authErrors.ts` (by `AuthApiError.code`, then text). Jest cannot see the router rewriting the address: after touching this flow, also check the exported web build in a browser.
- House reminders ("Avisos da casa"): `planHouseReminders` in `src/domain/houseReminders.ts` is the pure plan; each device chooses its kinds (`HOUSE_REMINDER_KINDS`: bills, documents, chores, appointments, events, vaccines, weather, eve). The `eve` kind ("Resumo de amanhã") is one notification at 20:00 on each of the next 7 evenings whose next day has something (`eveSummary`: consultas, family commitments and birthdays (`calendarEntries` of that day, so a "não vai ter" day is out and who takes / picks up is that day's), bills, vaccines, chores and manutenções, documents, warranties; only dates the data already has, never the Agenda's "previsão" repetitions; autopay bills and routine stay out, routine being a chore that is `daily` with an interval up to `EVE_ROUTINE_DAYS` (3) or a weekly commitment occurrence with the usual people (`entry.routine`), which would make it ring every night or every other night with nothing new; a new source of items is one entry in `EVE_ORDER`, its field in `EveSummaryInput` and one list in `eveItems`). Order: what has a time first, consultas and commitments together by the hour (same hour, the consulta first), then commitments without a time, birthdays and the rest source by source. The summary lists the commitments whatever the `events` kind says: the kinds only decide each thing's own reminders. Item texts: a commitment is "16h Festa do João (Ana, Carla leva)" (short time, title and `entryShortDetail`: whose it is and the ride, with the name only once when the commitment belongs to who takes, or to who only picks up: "Beto leva e busca") and a birthday "Aniversário de Ana (faz 8 anos)"; a bill without a value is "Conta: X" (unless its name already starts with "Conta"); a vaccine is "Vacina de Bia: …" ("de", because "da"/"do" would guess a gender), and two or more of the same person are one item ("Vacinas de Bia: A e B"); a consulta with no "2 horas antes" reminder (before 9h, `appointmentLeadTime`) carries its place, and a commitment whose day reminder does not exist (before 1h) or would ring before 07:00 (`EVENT_EARLY_TIME`) carries its place and "Levar: …" ("6h30 Passeio (Ana, Carla leva), Portão 2. Levar: lanche": what the 19:00 reminder that the summary replaces would have told; a later commitment, or one without a time, leaves both to its own day reminder). Those tails only get the room the items leave: first every place, in the order of the items, then each "Levar: …" (only after that item's whole place), each one whole, cut with "…" or left out when less than its minimum is left (`EVE_PLACE_MIN`, `EVE_BRING_MIN`); a commitment's "Levar" never takes the place of a later consulta. The text: at most 4 items written (with more, 3 and "e mais N") and 180 characters. When they run short, the plain cut (`fitTexts` over the whole texts: the longest are cut with "…" at the end, the short ones stay whole) is the starting point, and it is what every item that is not a commitment gets, always: a bill, a vaccine or a consulta never shrinks for a commitment's sake. The plain cut also stays for the commitments when it leaves every parenthesis readable (whole, or missing only the end of its last verb, with at least `EVE_VERB_MIN` letters of it: "Vó Maria bus…"). Otherwise (`fitItems`) each commitment's parenthesis is kept apart (`EveItem.detail`) and whole, and the commitments' titles (a commitment without a parenthesis is all title) share what the parentheses and the other items' plain cut leave. A commitment whose cut title would keep fewer than `EVE_TITLE_MIN` (12) letters, not counting the hour, goes back to its plain cut, with the room that cut gave it, and the others share the rest. A cut inside a parenthesis of the title itself moves back to before it when 12 letters remain, and no cut leaves a loose comma or a just-opened parenthesis (" (", " (A", " (An") before the "…". A day with only bills still gets its summary (the bill's own 9h reminder is another moment). While the kind is on, a consulta or a commitment written in a summary (not one left in the "e mais N", and only where that evening has a summary) gets no 19:00 eve reminder of its own (the hint in the settings list says so; `carried` is keyed by source and id, a commitment occurrence being id@date as in its reminder keys), and that summary takes the place of that 19:00 reminder in the limit queue: `standIn` for a consulta's (ahead of every other 19:00 of that evening), `forEvents` for commitments' only (exactly where the first eve it replaces would sort). A summary that stands in only for commitments counts in the commitments' part of the limit, like the eve it replaces; past that part it is a plain summary (with the kind off that eve would not fit either). If plain summaries of earlier evenings would still push a stand-in out, the farthest kept plain summary leaves and the cut is redone. So turning the kind on never costs a consulta or a commitment an eve warning that a summary replaces (a test over random houses pins it), except between 19:00 and 20:00, when tonight's summary is an extra reminder in the place of an eve that has already passed; an own 19:00 that no summary carries (an evening beyond the 7 nights, or an item left in the "e mais N") is subject to the accepted cost below. The limit: the family commitments are first cut to their share (see the Family calendar note), and the rest is one sort: own reminders by the time they ring, and the plain summary of evening D right after every own reminder dated up to D+1 (the day it talks about) and before those dated D+2 or later; then the plan is cut. So a plain summary never displaces a reminder of the day it talks about or of earlier days (a commitment of those days can still be out because of its share), and the farthest evenings go first. Accepted cost: with the summary on, an own reminder two or more days away may wait for the window to move (the plan is redone every time the app opens); in a house whose routine of commitments fills the free places, that happens at the default limit too. With the kind off the plan is exactly what it was before the kind existed. `syncHouseReminders` holds the kind as unknown (what is scheduled stays, nothing is replanned) while consultas, vacinas, the family calendar (`family`) or the equipment list have not loaded (on a database without the commitments tables the calendar still arrives, with the people only, so the summary does not wait); `eve` enters the unknown set only when the kind is on, so nothing changes for a device that does not use it. Two accepted corners of that held state, both gone at the next complete sync: the consulta's own 19:00 (and the commitment's, when what is missing is not the family calendar) is planned again next to the held summary (two notifications that night rather than none), and the held summaries keep their slots, so under a short limit the farthest own reminder can be left out (charging the held summaries last is not safe: it could cancel the only eve warning of a consulta). In the notification data the summary carries `reminder: <key>:<householdId>`, because on web that value is the notification tag and the summary key has no record id (two houses on the same evening would replace each other); the plan key has no house in it (the stored signature is the plan plus `|casa:<householdId>`, as for every kind: that suffix is what re-schedules, once, the reminders saved before their data carried the house, so it must stay), and the weather tip (`weather:dia:…`) still shares its tag between houses.

- Family calendar ("Compromissos da família"): `family_events` has one row per compromisso; a repeating one is the rule (weekly on `weekdays`, monthly, yearly, optional `until_on`) and its dates are computed in the app, never stored. `family_event_days` holds what changes on one date, keyed by (event, date): `cancelled` ("Não vai ter neste dia") or `override_take`/`override_pick_up` with a nullable person id (override + null = nobody that day: the occurrence carries it as `nobody_takes` / `nobody_picks_up`, every text built from `calendarEntries` says so, "Ninguém leva, Carla busca", through `rideText`'s `nobody`, and that occurrence is never `routine`, also when the compromisso usually has nobody there, which is the day whose one-day driver was deleted; no override = as usual; a row with nothing changed is not kept, and a row whose date left the series, or any row once the compromisso no longer repeats, is ignored and cleaned on save; saving the series also drops the day changes that became equal to the new usual PERSON, `dayChangesAfterSave`; a marked change with no person is never "equal to the usual", `normalizeDayChange` keeps it also when the usual is nobody, so saving the commitment never erases a "Ninguém leva" day unless the date leaves the series (the stale-date cleanup just described): while the date is still of the compromisso, only "Como sempre" or another person chosen for that day does, and the day card shows the "Ninguém" chip for it). `take_by`/`pick_up_by` are `people` of kind 'pessoa' (trigger). Deleting the record of the usual person clears the name; deleting, or turning into a pet, the record of who covered ONE day leaves that day with nobody and its change still marked, so it reads "Ninguém leva": the day leaves the routine and its eve reminder says so, which is what the house needs to hear. The commitment form copies the row into its fields once, so `compromisso/[id].tsx` waits for the fetch of this visit before mounting it (a cached copy may predate a change made here or on another phone, and saving would write it back). The editor always reads on open, also when the cache is younger than the stale time (`useFamilyEvent` and `useFamilyEventDays` with `fresh`, `refetchOnMount: 'always'`). With a cached copy the wait is bounded (4 s, so a network that does not answer cannot hold the screen), offline the fetch is paused, and a fetch that fails with a cached copy is not a full-screen error (that is only for a failure with nothing cached): in all three cases the cached copy opens, and when the row that arrives later differs from the one the fields were filled from (`sameEventFields`) the form says so, offers "Atualizar" (a remount with the current row) and asks before saving over it. Until a fetch of this visit has succeeded the copy is not `confirmed` (`isSuccess && isFetchedAfterMount`, latched per id: `isFetchedAfterMount` alone is also true after a failed fetch, and a later failed refetch does not undo it; a new compromisso is always confirmed): the form shows the card "Cópia guardada neste celular" (with "Tentar de novo" when no fetch is in flight, i.e. it failed or is paused, or when the one in flight has not answered after another 4 s), Salvar asks first with words of its own ("Não deu para conferir"; one question per tap, and the answer stands if the fetch arrives while it is open) and the "Só neste dia" choices stay disabled; a fetch that arrives equal removes the card silently, one that arrives different hands over to "Este compromisso mudou" (never both). "Changed elsewhere" means the row matches nothing this form knows (`known`: the row the fields were filled from, then the values of every `save.mutate`, in order; with a second save in flight the row is still the first one's), so the person's own save never raises the notice or the question, in flight, after failing halfway (row updated, day cleanup failed) or after succeeding with the form still mounted (a web tab with nothing to go back to). When the row arrives equal to something the form sent, everything before it is dropped from `known`: a later change from another phone raises the notice and the question again, also when it puts the commitment back exactly as it was when the form opened. Offline with nothing cached (the single-commitment query paused with no data) the screen says "Sem internet: não deu para abrir este compromisso." with "Tentar de novo" instead of spinning, and the form opens by itself when the query resumes (it is not seeded from the list). Once the form is on screen a later refetch or its failure never takes it away (a latch per id); only a refetch that finds the commitment gone replaces it with "Compromisso não encontrado". The "Só neste dia" choices write the whole day row from what is on screen and `normalizeDayChange` compares it with the commitment's usual people, so they do not accept taps until a fetch of the day changes made for this visit has succeeded and the commitment is confirmed. A day-changes fetch that failed, is paused or has not answered after the same 4 s shows a line with "Tentar de novo", inside the day card when day changes are cached and in its place when nothing is; the button restarts that request (`useRestartFamilyEventDays`, cancel + refetch: TanStack's `refetch()` only replaces a running request when the query already has data) and also refetches the commitment when it is unconfirmed with no fetch in flight or with one that has not answered after 4 s. A day write refused for a person key (23503: that record was deleted on another phone) has its own sentence (`FAMILY_EVENT_DAY_PERSON_GONE` through `familyEventDayErrorMessage`; `FAMILY_EVENT_PERSON_GONE` stays for Salvar and `FAMILY_EVENT_GONE` for the commitment key) and invalidates `['people']` and `['familyEventDays']`, so the chip leaves the choices. `saveFamilyEvent` asks for the updated row back: no row means the commitment was deleted on another phone, and the save fails with `FAMILY_EVENT_GONE` instead of closing the screen as if it had saved. Everything pure lives in `src/domain/familyEvents.ts`: `calendarEntries` is the one expansion (occurrences with day changes + birthdays) used by the agenda (`buildAgenda`), the Hoje section (`todayEntries`), the Nuke snapshot (`calendarLines`; when the period has more lines than the snapshot writes, `NUKE_LIST_LIMIT`, the routine occurrences go last, so what falls into "e mais N" is the routine and not the one-off commitment, the changed day or the birthday), the evening summary (`eveSummary`, which leaves the routine out) and the reminders (kind `events`: eve at 19:00, one hour before (none when that would be before midnight, i.e. for a time before 01:00), 08:00 for all-day and for birthdays (a birthday has no eve); a weekly occurrence gets only the day reminder unless that day changes who takes or picks up (`routine`) or the day reminder is missing or would ring before 07:00; with the `eve` kind on, an occurrence written in that evening's summary has no 19:00 of its own, and when its day reminder is missing or before 07:00 the summary also tells its place and "Levar: …"; in `planHouseReminders` the events get at most half the limit (rounded up, so one place over half when the limit is odd), or the places the other kinds' own reminders leave free, before the global cut; a plain evening summary is not counted there (it takes its turn in the queue), one that stands in for a consulta's eve counts as that own reminder, and one that stands in only for commitments' eves counts in the events' part); it starts near the range, never counting from `starts_on`. Birthdays come from `people.birth_date` (no table; 29/02 on 28/02; the birth year is not a birthday). The app may ship before the migration: `src/data/family.ts` answers "no compromissos" when the tables are missing (`isMissingTable`), screens read them through `useFamilyCalendar` and keep those two queries out of their error and "everything loaded" lists, and saving shows `FAMILY_EVENTS_UNAVAILABLE`. Not in the persisted cache.
- Shopping list ↔ receipt: list items are free text, so `confirm_receipt` removes the list items the user ticked in the review and learns `list_item_links` (list name key → product). Matching and keys live in `src/domain/listLinks.ts` (`listNameKey` must match the SQL check on `name_key`); the cart/receipt pantry de-duplication (`src/domain/cartPantry.ts`) uses the same links. The review also keeps product names standard (`src/domain/similarNames.ts`; what each tap does to the item is in `src/domain/receiptNames.ts`): a new product's name is checked against one index of the names the household already uses (products, open list items, recent purchases) plus the `COMMON_ITEMS` catalog. `igual` is the same words ignoring accent and plural, and ignoring order only when neither name has a role link ("Suco de laranja" is not "Laranja para suco"); sizes ("350ml", "1,5L" as one decimal size, "2 litros" = "2L"), a trailing letter ("Vitamina C") and "sem X" count as part of the name. `parecido` is one name containing the other. The product picker shows up to 5 similar names (among the loosely similar ones, household names come before catalog ones), including the names given to other items of the same receipt ("Nesta nota", a second small index). `suggestedName` is what the item card offers unprompted and must be high precision (in doubt, no chip): the best `confident` household name, never a catalog-only one. Confident means the household name fits at the start of the new name with the same size and what follows does not make another thing ("de"/"em" plus a non-packaging word, a word of the fixed `OTHER_THING` set such as "Leite coco", or a pair that some indexed name knows as one name, joined by "de"/"em" or by a hyphen: "Pão de queijo", "Couve-flor"; a hyphen nobody knows, as in "Banana-prata", is just a variety); a household product with a real size is exact (same sizes, so a pack is not the unit; after it only packaging words or a version word with its number, "Tipo 1") and only it may fit in the middle of a name. The catalog does not silence the household's generic name ("Leite" for "Leite Integral Italac 1L"); a longer indexed name, catalog or household, vetoes the chip only when it also fits the start loosely and is another thing ("Leite condensado" for "Leite cond moca"). A receipt abbreviation ("DETERG") counts when the fragment has a single reading, is at least half the word, does not end in a vowel and is not a real word; the vocabulary of real words is the catalog plus list items and purchases without a product, and a product's word only when it is not the start of a longer one. It only suggests: nothing is linked or renamed without a tap, and after "Usar" the card shows "Desfazer", which puts the item's override back exactly. The list tick is derived, not stored: `matchListItems` ticks a list item while the receipt line's product has its name; the review passes `sameListedName` for that, the same `igual` rule ("Limões" with the product "Limão", but not "Molho de tomate" with "Tomate para molho"), while `listRemovals` still sends the list item's own name and `listNameKey`. The list screen's market estimate (`src/domain/listEstimate.ts`: `estimateList` for the total and each item's cost, `pantryHits` for "Na despensa", `itemFacts`, `describeEstimate`, `estimateHeadline` and `describePantryHits` for the texts) and "Onde comprar" (`recommendation.ts`) are one calculation: the price of each list item in each store comes from one rule, `listStorePrices` in `listEstimate.ts`. The item's product is its own or, when it has none or that product has no price, the most recently bought among the products linked to the name via `LinkIndex.productsFor` and the same-name product (when two products have the same name but for the accent, the one with the most recent price, then the lowest id, never array order); in a store, the price is that product's in its usual unit, then that product's in another unit, then, only when the product came from the name (the item has no product, or its product has no price anywhere), another product's linked to the name (always shown as approximate, "~"), and for a store without any of them the product's average times the store's price level (`storePriceIndex` in `src/domain/priceLevel.ts` over all the household's prices: positive prices only, one price per store in each product (the newest when the rows carry `purchasedAt`, else the store's average), shrunk towards 1 when few products are shared, clamped). Which texts a numeric row reads is one rule, `sameItemText`: the same occurrence in the report and the row's own family (the percentage row reads the "%" texts and, when only the unit says percentage, as in "Hemoglobina glicada" in %, also the bare-name texts that came without a unit; the unit-less "#" row reads the "#" texts; the unit-less bare row the bare ones; a row with a real unit other than "%" reads the bare and the "#" texts, because "Leucócitos #" and "Leucócitos" in /mm³ are one series), and never a text that some report brings beside that number (the EAS dipstick "Negativo" beside the sediment count of the same name): those are two measures, like two unit groups that share a report, so a row may stay without a note that would have been true (a curve where one sample came as text). `valueLabel` glues "%" only to a value that ends in a digit ("5,6%", "< 0,5%"; a text with "%" in the unit field is "Não realizado %"). `changeSentence` does no arithmetic with "<"/">" or when one value is ten times the other or more, uses percentage points when the unit as written is "%" with no letter or digit glued to it ("%", "% (NGSP)", "% do total"; not "%o" nor "mg%"; the unit groups still come from `normalizeUnit`, so "%" and "% (NGSP)" are two groups), and a series with a bound in it ("< 0,5", "> 5") or mixing "1.020" (ambiguous thousands) with "1,015" gets no chart. Each list is ordered on purpose: what the last report flagged comes first (it is what asks for attention), then the most recent, and items of the same date follow the order of the report. The app never judges normal/abnormal and never reads reference ranges: it shows the stored flag, the reference as written and the change.
